# SPLAT!

2~4인이 함께 즐기는 온라인 파티 게임. 협동 모드(열쇠·문·압력판·이동발판 등 기믹을 풀며 전원 골인, 13개
스테이지)와 경쟁 모드(라운드제 미니게임 10종으로 순위 경쟁)를 지원합니다.

## 이 게임은 서버 없이 파일 하나로 동작합니다

`client/index.html` **파일 하나**에 게임 전체(HTML/CSS/JS, 협동·경쟁 게임 로직, PeerJS 라이브러리까지)가
전부 들어있습니다. 자체 서버를 따로 돌릴 필요가 없습니다.

**어떻게 서버 없이 되냐면**: [PeerJS](https://peerjs.com)(WebRTC 기반)를 씁니다. 방을 만든 사람의
브라우저가 곧 "서버" 역할을 맡아서 게임 로직(협동/경쟁 판정, 물리 시뮬레이션)을 그대로 실행하고,
다른 참가자들은 브라우저 대 브라우저로 직접(P2P) 연결됩니다. PeerJS의 무료 공개 브로커 서버는 "두
브라우저가 서로를 찾도록" 최초 신호(signaling)만 도와줄 뿐, 실제 게임 데이터는 중간 서버를 거치지
않고 참가자들 사이에서 직접 오갑니다.

## 실행 방법

**꼭 `http://` 또는 `https://` 주소로 열어야 합니다.** 파일을 더블클릭해서 `file://`로 직접 열면
(특히 "참가하기" 쪽이) 브라우저가 이 페이지를 신뢰할 수 없는 출처(origin: null)로 취급해서 PeerJS
서버와의 통신이 CORS로 막힐 수 있습니다. 아래 두 방법 중 하나를 쓰세요.

**방법 1 — 깃허브 페이지(추천, 가장 간단)**
1. 이 저장소를 깃허브에 올리고 `client/index.html`을 저장소 루트(또는 원하는 경로)에 둡니다
2. 저장소 Settings → Pages 에서 GitHub Pages를 켭니다
3. 발급된 `https://내계정.github.io/저장소명/...` 링크로 접속 — 이게 진짜 `https://` 주소라 문제없이
   작동합니다

**방법 2 — 로컬에서 임시 웹서버로 열기 (인터넷 없이 같은 컴퓨터/네트워크에서 테스트할 때)**
```bash
cd client
python3 -m http.server 8000
```
그 다음 브라우저로 `http://localhost:8000` 접속. (Node가 있다면 `npx http-server` 등도 가능합니다.)
이렇게 하면 `http://localhost`도 브라우저가 신뢰하는 주소로 취급하기 때문에 정상 작동합니다.

설치할 패키지나 실행할 백엔드 서버는 없습니다 — 위 두 방법 다 "정적 파일을 웹 주소로 서빙"만 해주면
됩니다.

## 플레이 방법

1. 한 명이 "방 만들기"를 누르면 4자리 방 코드가 나옵니다 (이 사람이 호스트가 됩니다)
2. **로비 화면에서 방 코드 아래에 "⏳ 참가자를 받을 준비 중..." 문구가 "✅ 참가자를 초대할 수
   있습니다"로 바뀔 때까지 잠깐(보통 1~2초) 기다린 다음 코드를 공유하세요.** 이 문구가 뜨기 전에
   코드를 공유하면 참가자가 "방을 찾을 수 없습니다" 오류를 받을 수 있습니다 (아직 신호 서버에 방
   등록이 끝나지 않은 상태라서 그렇습니다).
3. 코드를 다른 사람에게 알려주면, 각자 자기 브라우저에서 같은 `index.html`을 열고 "참가하기"에
   코드를 입력합니다
4. 로비에서 모드(협동/경쟁) 선택 후 호스트가 "게임 시작"

### "방을 찾을 수 없습니다" 오류가 뜬다면
- 방장 화면에서 "✅ 참가자를 초대할 수 있습니다"가 뜬 뒤에 코드를 공유했는지 확인하세요
- 방장/참가자 둘 다 `file://`이 아니라 `http://`/`https://` 주소로 열었는지 확인하세요 (위 "실행
  방법" 참고)
- 방 코드를 정확히 입력했는지 확인하세요 (대소문자는 자동으로 맞춰주지만 글자 자체는 정확해야 합니다)
- 그래도 안 되면 잠시 후 다시 시도해보세요 (PeerJS 무료 브로커가 일시적으로 불안정할 수 있음)

## 중요한 제약 사항 (정직하게 명시합니다)

- **`file://`로 직접 열면 (특히 "참가하기" 쪽이) 작동하지 않을 가능성이 높습니다.** 코드를 확인해보니
  방장은 미리 정해둔 ID로 Peer를 생성해서 file://에서도 될 수 있지만, 참가자는 PeerJS 서버에 ID를
  먼저 fetch로 받아와야 하는데 이 요청이 file:// 출처(origin: null)에서 CORS로 막힐 가능성이 있습니다.
  실제로 이 문제가 재현되는지 이 환경에서는 네트워크 제약상 최종 확인은 못 했지만, 코드 구조상 위험
  요소가 명확히 있어 **반드시 `http://`/`https://` 주소로 열도록 안내합니다** (위 "실행 방법" 참고).
- **호스트가 브라우저 탭을 닫거나 새로고침하면 게임이 끝납니다.** 호스트의 브라우저가 곧 서버 역할을
  하기 때문에, 호스트가 나가면 다른 참가자들의 연결도 함께 끊깁니다. 방장 이양이나 서버 이전 같은
  기능은 없습니다.
- 최대 4명까지 호스트 브라우저에 직접 연결되는 구조(스타 토폴로지)라 인원이 많아질수록 호스트의
  네트워크/기기 성능에 어느 정도 의존합니다. 4명 기준으로는 문제없이 검증했습니다.
- PeerJS의 무료 공개 브로커는 트래픽이 몰리거나 일시적으로 불안정할 수 있습니다. 연결이 안 되면
  잠시 후 다시 시도해보세요.
- 방화벽이 매우 엄격한 네트워크(일부 회사/학교망)에서는 WebRTC P2P 연결 자체가 막혀있을 수 있습니다.

## 게임 모드 설명

### 협동 모드 (13개 스테이지, 난이도 점증)
- 흐름: 인트로 → 카운트다운 → 플레이 → (열쇠 수집 → 문 개방 → 전원 골인) → 클리어/실패 → 결과 → 다음 스테이지
- 스테이지1~13: 기본 열쇠/문부터 시작해 이동 발판으로 구멍 건너기, 2인/전원 동시 압력판, 역할 분담
  (서로 다른 발판·열쇠를 나눠 맡기), 여러 관문을 순서대로 통과하기까지 점점 복잡해집니다
- **한 명이라도 탈락(구멍에 빠짐 등)하면 그 즉시 팀 전체가 실패 처리됩니다** (PICO PARK류 협동 게임의
  핵심 규칙). "다시 시도" 버튼으로 같은 스테이지 처음부터 재시작합니다

### 경쟁 모드 (미니게임 10종, 매 라운드 랜덤 로테이션)
방장이 라운드 수(3/5/7/10)를 설정하면, 매 라운드 아래 10종 중 하나가 무작위로 나옵니다(직전 라운드와
중복 없음). 순위별 점수(1위 10점/2위 7점/3위 4점/4위 2점)를 누적해 최종 순위를 가립니다.

| 게임 | 핵심 요소 | 요약 |
|---|---|---|
| 밀어내기 | 반응속도+판단력 | SPACE로 공격해 원형 경기장 밖으로 밀어내기 |
| 초 정확히 맞추기 | 반응속도+판단력 | 목표 시간에 정확히 SPACE |
| 꼬리 잡기 | 반응속도+눈치 | 접촉으로 꼬리를 뺏고 뺏기며, 보유 시간이 길수록 고득점 |
| 레이스 | 반응속도+판단력 | 장애물을 피해 결승선까지 먼저 도착 |
| 폭탄 넘기기 | 운+눈치 | 랜덤한 시점에 터지는 폭탄을 넘기며 생존 |
| 영역 점령 | 판단력+눈치 | 구역에 혼자 머물러 점유도를 올리기 |
| 색깔 밟기 | 반응속도+눈치 | 지정된 색 발판을 제한시간 내에 밟기 |
| 보물 쟁탈 | 운+판단력 | 랜덤 등장하는 보물을 먼저 차지하기 |
| 반응속도 | 반응속도+눈치 | 신호가 뜨면 최대한 빨리 SPACE |
| 낚시 | 운+판단력 | 입질 타이밍에 맞춰 E로 낚아채기 |

## 개발 환경 / 프로젝트 구조

```
party-game/
  client/
    index.html        # 게임 전체 (단 하나의 파일 - 이것만 있으면 됩니다)
  server/              # (선택) Node.js 전용 서버 - 아래 "레거시" 항목 참고
  shared/
    constants.js       # server/의 Node.js 코드가 참조하는 공용 상수 (client는 이미 인라인됨)
  test/                # 자동화 테스트 (아래 "검증 현황" 참고)
  package.json         # server/를 돌릴 때만 필요
```

`client/index.html` 안에는 순서대로 다음이 전부 인라인되어 있습니다:
- CSS 전체 (`<style>`)
- 공용 상수 (원래 `shared/constants.js`)
- **PeerJS 라이브러리** (CDN이 아니라 통째로 인라인 - 외부 스크립트 태그 의존성 없음)
- **협동/경쟁 게임 로직** (원래 `server/`의 Room, Player, CoopEngine, CompetitionManager, 미니게임
  10종을 Node.js 전용 문법(require/module.exports) 없이 브라우저에서 그대로 실행되도록 이식한 것)
- 새로운 `Net` 모듈 — PeerJS 기반 P2P 통신 계층 (아래 설명)
- 나머지 클라이언트 모듈 (input, camera, render, sound, ui, app)

### `Net` 모듈이 하는 일 (PeerJS 기반 P2P)

- **방 만들기**: `new Peer(네임스페이스 + 방코드)`로 그 방 코드를 자신의 피어 ID로 등록하고, 로컬
  Room 인스턴스를 만들어 자기 자신을 첫 번째 플레이어로 즉시 추가합니다 (신호 서버 연결을 기다리지
  않고 로컬 플레이는 바로 시작 - 신호 서버가 늦거나 실패해도 최소한 그 화면에서는 계속 플레이 가능).
- **참가하기**: 익명 `Peer`를 만들고 `peer.connect(네임스페이스 + 방코드)`로 호스트에게 직접 연결한
  뒤, 원래 서버가 처리하던 것과 동일한 형식의 메시지(`JOIN_ROOM`, `INPUT` 등)를 데이터 채널로 주고
  받습니다.
- 호스트 쪽에는 원래 `server/index.js`의 메시지 라우팅 switch-case를 그대로 옮긴 `hostHandle()` 함수가
  있어서, 여러 참가자의 연결을 각각 독립적인 상태로 관리합니다 (최대 4명, 스타 토폴로지).
- 메시지 형식(`{type, payload}`)과 UI/렌더링 코드는 기존과 완전히 동일합니다 - 바뀐 것은 오직
  "메시지가 어떻게 전달되는가"뿐입니다.

### `server/` 폴더는 레거시입니다

이 프로젝트는 원래 Node.js + WebSocket 전용 서버로 시작했었고, `server/` 폴더에는 그 코드가 여전히
남아있습니다 (완전히 동작하며 테스트도 통과합니다). 하지만 **현재 `client/index.html`은 이 서버를
전혀 사용하지 않습니다** — 위에서 설명한 PeerJS 기반 P2P로 완전히 대체되었습니다.

자체 서버를 직접 운영하고 싶다면(예: 항상 켜져있는 전용 서버가 필요한 경우) `server/` 코드를 참고용
레퍼런스로 쓸 수 있지만, 현재 `client/index.html`과 다시 연결하려면 별도의 WebSocket 클라이언트 코드를
새로 붙이는 작업이 필요합니다 (예전에 있었지만 지금은 PeerJS `Net` 모듈로 완전히 교체되었습니다).

### 검증하지 못한 것 (숨기지 않고 명시합니다)
- **PeerJS의 실제 공개 브로커 서버(0.peerjs.com)와의 실제 WebRTC 시그널링은 검증하지 못했습니다.**
  이 프로젝트를 만든 샌드박스 환경 자체가 그 도메인으로 나가는 네트워크를 차단하고 있어서, 대신
  동일한 PeerJS 클라이언트 API를 그대로 구현한 가짜 신호 릴레이로 우리 쪽 코드(연결 로직, 메시지
  처리, 게임 로직)를 검증했습니다. 실제 브로커와의 연결 자체는 PeerJS 라이브러리의 표준 동작에
  의존하며, 문서화된 API를 정확히 그대로 사용하고 있습니다. **실제 배포 환경에서 두 사람이 진짜로
  접속해보는 최종 확인이 필요합니다.**
- 4인 이상의 실제 WebRTC P2P 연결(스타 토폴로지, 호스트가 3개의 별도 연결을 동시에 유지)은 로직상
  구현되어 있지만 실제 네트워크로는 검증하지 못했습니다.
- 방화벽/NAT 환경에 따른 WebRTC 연결 실패 케이스(예: symmetric NAT)는 PeerJS가 기본 제공하는 STUN
  서버로 대부분 처리되지만, 모든 네트워크 환경에서의 동작을 보장하지는 못합니다.
